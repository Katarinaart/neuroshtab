## РЕЖИМ LAUNCH — новый проект

### Шаг 1 — Intake (вопросы по одному)
1. Название/slug проекта
2. Что строим и первый user journey
3. Surfaces: web / mobile / backend / landing / full-stack (остальные — deferred)
4. Нужны ли в v1: auth, persistence, file uploads, payments, admin, интеграции
5. Real-time: чат, presence, live notifications
6. Деплой сейчас? Если да — production domains

### Шаг 2 — PRD-интервью → PRD.md (в текущем окне)
Вопросы по одному с вариантами ответа. Итог — `projects/{name}/PRD.md` без
размышлений и открытых вопросов: только чёткое ТЗ.

### Шаг 3 — Проверка PRD (НОВОЕ ОКНО)
В чистом независимом контексте: "Проверь PRD на открытые вопросы и противоречия."
Обновить PRD по результату.

### Шаг 4 — TASKS.md (НОВОЕ ОКНО)
В чистом контексте разбить PRD на `projects/{name}/TASKS.md`.
Каждая задача атомарна, выполнима за одну сессию:

```
- [ ] TASK-001: Название
  Что: конкретный результат
  Edge cases: что может пойти не так
  Acceptance: как проверить что готово
```

### Шаг 5 — Форк vibe
```bash
git clone https://github.com/di-sukharev/vibe {project-name}
cd {project-name}
git remote remove origin
bun install
```
Дальше — `Agent Repo Download Instructions` из README шаблона.

## РЕЖИМ OPERATIONS — текущие задачи

### Перед задачей
1. `TASKS.md` — первая незакрытая задача
2. Обсудить edge cases и план до кода
3. Ориентация в коде: `tree -L 2/3`, потом узкий `rg "символ"` —
   **не начинать с широкого поиска по общим словам**
4. Широкое чтение репозитория — cheap read-only subagent, не основная модель

### Классификация

| Тип | Когда | Процесс |
|---|---|---|
| Direct | Косметика, copy, очевидные правки | Минимум, быстрая проверка |
| Investigation | Дебаг, root cause непонятен | Трассировка пути выполнения |
| TDD-first | Логика, auth, persistence, валидация, state | RED → GREEN → REFACTOR |

### Acceptance contract (для нетривиального, до кода)
- Что значит "done"
- 3-5 pass/fail критериев
- Primary signal (user-visible или runtime)
- Secondary signals (tests, typecheck, lint, build)

## ОБЯЗАТЕЛЬНЫЙ PIPELINE

```
Риск-субагент (новое окно) → Обсуждение + Plan Mode (текущее окно)
→ Git worktree → TDD → Реализация
→ Serious bugs review (новое окно) → Loop-review до 9.5/10
→ Merge/PR
```

### Риск-субагент ДО кода (НОВОЕ ОКНО)
Перед реализацией — запустить субагента с чистым контекстом:
```
Прочитай задачу TASK-XXX из TASKS.md и PRD.md.
Выдай список рисков, edge cases и потенциальных проблем
которые нужно учесть до начала реализации.
```

### Plan Mode
В текущем окне после обсуждения рисков — переключить в режим планирования.
Получить явное одобрение плана до начала реализации.
Для крупных фич — план как отдельный артефакт.

### Git worktree
Изолированная ветка под каждую задачу. Не работать напрямую в main.

### TDD (для нетривиального поведения)
RED → GREEN → REFACTOR. Строго.

E2E — user-visible behavior через слои.
Integration — API/auth/persistence/contracts.
Unit — только когда дают отдельный локальный сигнал.

### Serious bugs review (НОВОЕ ОКНО — обязательно)
После реализации, в чистом независимом контексте:

```
Сделай глубокое code review активных изменений. Работай read-only, ничего не меняй.
Задача — найти серьёзные баги, которые в проде бы лопнули: регрессии, ошибки логики,
проблемы безопасности/приватности, потерю данных и места, где не хватает важных тестов.
Проверь не только diff, но и связанные места по цепочке:
route/guard → handler/service → API contract → persistence/external services.
Верни только подтверждённые проблемы: severity, file:line, доказательство по коду,
риск, минимальный fix и какой тест это должен поймать.
```

Роли субагентов: регрессии / лишний код / баги / security+best practices /
"можно ли меньше кода" / элегантность.

**Findings reviewer — не команды к слепому исполнению.** Основной агент сам
решает какие замечания принять, какие оспорить. Принимать только подтверждённые.

### Loop-review (скил `/loop-review`)
Гонять до 9.5/10 или до отсутствия actionable comments.
Токены на ревью лучше чем баги в проде.

### Completion protocol
- Что изменено и почему
- Root cause (если investigation)
- Валидация выполнена
- Primary signal: met / not met / partially validated
- Что ждёт деплоя / подтверждения
- Suggested commit message

Задача не закрыта если симптом устранён, но механика структурно несогласована.

## CARE-REFACTORING

Раз в две недели или когда накопилась боль в DX/поддержке:
1. Найти объективно сложный в поддержке код (не эстетика)
2. Покрыть важное поведение тестом
3. Аккуратно переписать/упростить с сохранением бизнес-логики

**UI-правило:** стили компонента живут внутри компонента. Снаружи — только
layout/composition, никаких хаотичных `style`/`className` overrides снаружи.

В production — рефакторинг только с e2e/integration/unit тестами на изменяемое поведение.

## БЕЗОПАСНОСТЬ

### Security audit перед production (НОВОЕ ОКНО, повторять)
```
Проведи ультраглубокий аудит безопасности, мы скоро выходим в продакшн.
Проверь, что нет багов и слабых мест, из-за которых нас могут взломать.
Можно запускать субагентов на участки кода, спорить с ними и собрать список
правок по приоритету. Финально: список проблем, риск, план исправления.
```

Повторять в новых окнах пока не перестанет находить уязвимости.
Отдельно: endpoint ID enumeration — нельзя ли перебрать `id` и получить чужие данные.

### Supply-chain audit
При новостях о взломе npm-пакетов: read-only инвентаризация, проверка затронутых
версий и lockfiles, pin безопасной версии, убрать `^~`, не ставить `latest`.

## НАГРУЗОЧНОЕ ТЕСТИРОВАНИЕ (перед production)

1. Поднять отдельный контур максимально похожий на production
2. Агент читает реализацию и выписывает очевидные bottleneck под 3-5k RPS
3. Тест из отдельной VM в облаке, через open-source инструмент
4. Ступени: 1k / 3k / 5k / 10k RPS
5. Баги → `projects/{name}/notes/<note.md>`, потом задачи в `tasks/<task.md>`
6. Финальная документация: минимально достаточная стартовая инфраструктура
   (начальный tier managed Postgres, вертикальное масштабирование БД,
   горизонтальное масштабирование backend)

## МОНИТОРИНГ ОШИБОК (production)

Автоматизация раз в 30 минут: production logs → actionable инциденты →
`projects/{name}/errors/<error_name>.md` (trace, контекст, время).
Разбор `errors/` — отдельная сессия раз в день, по одной ошибке, удалять после фикса.
